# Labs 041-050 — GitHub Collaboration

## Lab 041 — Create a GitHub repository workflow
**Objective:** Connect a local project to a GitHub repository. **Commands:** Add origin, push main, verify the GitHub branch. **Expected:** Repository contains the project. **Task:** Compare local and remote history. **Challenge:** Start from an existing remote README and integrate safely. **Solution:** Clone when the remote already has content. **Interview:** Git vs GitHub?

## Lab 042 — Create a feature branch for a GitHub task
**Objective:** Use task-oriented branch naming. **Commands:** `git switch -c feature/add-login`; commit changes; push with upstream. **Expected:** Isolated remote branch. **Task:** Link the branch conceptually to an issue. **Challenge:** Use `fix/` and `docs/` naming. **Solution:** Pick consistent team conventions. **Interview:** Why avoid committing directly to main?

## Lab 043 — Open an issue
**Objective:** Write an actionable GitHub issue. **Scenario:** README installation instructions are incomplete. **Task:** Include title, context, reproduction, expected behavior, and acceptance criteria. **Expected:** Another developer can act without a meeting. **Challenge:** Add labels and milestone. **Solution:** Keep issue scope specific. **Interview:** What makes an issue actionable?

## Lab 044 — Build a pull request
**Objective:** Submit reviewable work. **Commands:** Push branch; open PR against main. **Expected:** PR shows commits and changed files. **Task:** Write a concise summary and testing section. **Challenge:** Link the issue. **Solution:** Reference the issue in the PR description. **Interview:** What should a PR description contain?

## Lab 045 — Review a pull request
**Objective:** Practice evidence-based review. **Task:** Inspect diff, tests, naming, error handling, and security. **Expected:** Comments are specific and actionable. **Challenge:** Separate blocking findings from suggestions. **Solution:** Explain impact and requested change. **Interview:** What is the purpose of code review?

## Lab 046 — Request changes
**Objective:** Simulate a review cycle. **Scenario:** PR misses tests for a new function. **Task:** Request tests, update branch, push again. **Expected:** PR updates automatically. **Challenge:** Add a regression test. **Solution:** Review should verify the new behavior. **Interview:** Does every review comment require a code change?

## Lab 047 — Squash a feature branch
**Objective:** Present a focused PR history. **Commands:** Make multiple commits; interactively rebase locally; push rewritten private branch with lease if necessary. **Expected:** PR contains coherent commits. **Task:** Compare squash merge vs rebase. **Challenge:** Preserve meaningful commits. **Solution:** Squash only when individual commits do not add useful history. **Interview:** What is a squash merge?

## Lab 048 — Use CODEOWNERS conceptually
**Objective:** Route reviews to responsible owners. **Task:** Create `.github/CODEOWNERS` with example ownership patterns. **Expected:** Ownership rules are understandable. **Challenge:** Assign docs and workflow paths separately. **Solution:** Use clear path patterns and team/user owners. **Interview:** What problem does CODEOWNERS solve?

## Lab 049 — Add issue and PR templates
**Objective:** Standardize contribution quality. **Commands:** Inspect this repository's `.github/ISSUE_TEMPLATE` and PR template. **Expected:** New issues/PRs have structured prompts. **Task:** Customize checklist items. **Challenge:** Add a security-reporting reminder. **Solution:** Keep templates concise and useful. **Interview:** Why use templates?

## Lab 050 — Simulate a complete issue-to-PR workflow
**Objective:** Integrate Git and GitHub skills. **Workflow:** Issue → branch → commit → push → PR → review → update → merge → delete branch. **Expected:** Traceability from requirement to merged change. **Task:** Document every transition. **Challenge:** Repeat with two contributors. **Solution:** Use small branches and review gates. **Interview:** Why is traceability valuable?
